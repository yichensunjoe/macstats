## 1. 一句话

0.3 的功能已经够用；当前瓶颈不是功能数量，而是三件事：

1. **没人看见**——仓库 14 天 1 次浏览，产品还没被放到任何人面前；
2. **不敢装**——未公证，非技术用户会被 Gatekeeper 拦掉；
3. **看到数字不知道下一步**——历史只知道“什么时候高”，不知道“是谁”。

未来两周不加 0.4 大功能，先完成四条轨道：**A 定位与信任、B 归因闭环、C 单渠道实验、D 发布护栏**。只有 B 是产品功能；A 是拍板，C 是实验，D 是基础设施。

## 3. 判断：这块面板到底卖什么

用户雇它，不是为了看六个数字，是为了**不打开活动监视器**就能回答两个问题：

1. **现在机器吃紧吗？**（3 秒内）
2. **刚才那阵卡，是谁造成的？**（10 秒内）

由这两问推出四条硬约束：

- **注意力稀缺**：桌面空间和瞥一眼的时间都有限。每个指标、每种语言、每张卡片都要证明自己值得占位。
- **信任是单次的**：一个数和活动监视器对不上，用户就再也不信整块面板；一次误杀进程，整块面板的可信度归零。
- **分发是乘数**：没人发现、或不敢装，功能价值就是 0。
- **维护是永久税**：10 份 README、两条展示路径、四档版式，每次发版都要付。税越高，越不敢发，越拿不到反馈。

### 3.1 现方案的五个矛盾

1. **受众与渠道自相矛盾**：北极星写“不写代码的 Mac 用户三次操作”，实际路径是 GitHub Release → 右键打开 → 终端。这类用户不会来 GitHub；开发者能接受右键，但“大白话进程解释”不是他们装它的首要理由。
2. **指标测的是结果，不是学习**：“7 天 50★ 或 300 下载”在 0 曝光下只是运气；没有假设、没有 kill criteria。
3. **功能在延长曲线，而不是回答问题**：30 天视图把一条不说明“是谁”的曲线拉长；告警只说 CPU 90%，不说谁干的。
4. **维护成本在限制迭代**：10 份 README 手工同步、无 CI、发布靠手抄清单；这次已经付过一次全量同步的代价。
5. **最危险的功能被当成卖点**：“一键清理”是唯一可能误伤用户东西的功能，却在没测过“实际回收”之前就写进 README。

### 3.2 由此得到的取舍

- **归因优先于时长**：先让 24 小时曲线能回答“是谁”，再谈 30 天。
- **曝光优先于功能**：先让 50 个真人看到并试用 0.3，再决定 0.4 加什么。
- **诚实优先于卖点**：清理不再把 RSS 求和说成“已释放”；先改文案，再谈测量。
- **单点优先于全面**：一个受众、一个渠道、一个安装路径；不同时讨好两类人。

## 4. 四条轨道

| 轨道 | 一句话 | 回答的问题 | 产出 | 依赖 | 人工决策 |
|---|---|---|---|---|---|
| **A 定位与信任** | 为谁做、叫什么、怎么装 | 谁会装？敢装吗？ | 一个受众、一个显示名、一条安装路径、许可证、首屏文案、反馈入口 | 无（H1–H2、H6） | 是 |
| **B 归因闭环** | 把数字变成答案 | 看到数字后能做什么？ | 历史点存 top 进程、峰值可点开、告警带原因、清理文案诚实 | B0 契约 | 否（范围已定） |
| **C 分发实验** | 把 0.4（或 0.3）放到 50 个人面前 | 有没有人真的需要？ | 一篇帖子 + 20 秒 GIF + 7 天数据 + 继续/停止决定 | A、D、B4（可选） | 是（H3） |
| **D 发布护栏** | 把发版变成一条命令 | 能不能每周发一次？ | CI、`release.sh`、文档一致性检查 | 无 | 否 |

### 4.1 每条轨道的最小结果

- **A**：能用一句话说清“给谁用”；Finder/README/Release/Cask 的名字一致；一台干净 Mac 按文档走一遍不需要你在旁边解释。
- **B**：点 24 小时峰值能看到“当时是谁”；高负载通知带进程名；清理结果不再把 RSS 求和说成“已释放”。
- **C**：一条渠道、一个帖子、一个 GIF；7 天后有下载数和至少 5 条可引用的反馈；做出继续/停止/改文案的决定。
- **D**：改一行版本号，CI 能指出哪份 README 没跟上；发一次版只需一条命令 + 一次实机安装。

## 7. 指标与决策门

### 7.1 C 的分发实验（唯一接触用户的轨道）

**假设**：目标受众看到 20 秒演示后，愿意下载并在 7 天内留下至少 5 条可引用的反馈。

| 指标 | 口径 | 记录时点 |
|---|---|---|
| 下载数 | Release 资产 `download_count` 的增量，**减去自己的校验下载** | 发布前基线、24h、72h、7d |
| 反馈数 | Issue / 邮件 / 私信 / 评论里能引用的一句话 | 7 天内 |
| 渠道流量 | GitHub traffic `referrers` / `views` | 7 天内 |
| 安装失败占比 | 反馈中“打不开/被拦截/不会装”的比例 | 7 天内 |

**决策门**（启发式，不是统计显著）：

| 结果 | 决定 |
|---|---|
| ≥50 下载且 ≥5 条反馈 | 继续：开第二个渠道；按反馈排 0.4.1 |
| 20–49 下载或 1–4 条反馈 | 只改一个变量（标题 / GIF / 渠道），再试一次；不碰产品 |
| <20 下载 | 停止加功能；找 5 个目标用户聊 15 分钟，重做 A |
| 安装失败 ≥30% | 先修 A（安装/公证/说明），不判断需求 |

**不看 stars 作为主指标**：star 是社交副产品，偏开发者，且不告诉你谁在用。

### 7.2 B/D/A 的验收

- **B**：见 [B §5](roadmap-v0.4/B-attribution-loop.md)。核心四条：老历史能读、新点有 top 3、峰值可点开、告警带原因。
- **D**：见 [D §5](roadmap-v0.4/D-release-infrastructure.md)。核心三条：CI 绿、文档检查能抓漂移、`release.sh --dry-run` 通过。
- **A**：见 [A §5](roadmap-v0.4/A-positioning-and-trust.md)。核心三条：ADR 落盘、名字一致、干净 Mac 走通。

## 9. 明确不做（这一轮）

- **不做 30 天视图**：数据已在存（`hourly(days:)` 已有），UI 晚点加不丢数据；它不回答“是谁”。
- **不做多显示器位置记忆**：等有人抱怨再排。
- **不加新语言**：10 份冻结，用 D2 脚本维护；新语言按真实需求。
- **不做风扇/温度/传感器**：需要特权或私有接口，风险高于收益。
- **不做 App Store / 内购 / 账号 / 云同步**：先证明有人愿意装。
- **不做 Intel 支持**：收益低、测试面大；继续写明 arm64 + macOS 15+。
- **不做 SIGKILL / 强制结束**：现有 SIGTERM + 确认的边界不变。
- **不做遥测**：不上报任何数据；实验只用 GitHub 公开计数与用户主动反馈。

## 11. 风险与回滚

| 风险 | 触发信号 | 缓解 / 回滚 |
|---|---|---|
| Gatekeeper 劝退 | 反馈里“打不开”占比高 | 先修安装文档；H4 改现在公证；不要靠“右键打开”硬撑非技术受众 |
| 改名混淆 | 老用户找不到、搜索仍被 macstats.app 压 | 保留仓库名与 Bundle ID；README 顶部加“原名 MacStats”一行；显示名可回退 |
| 历史文件变大 | 30 天 >50 MB | top 进程只在 CPU 超阈值时存；或只存名字不存路径；保留旧字段可读 |
| 告警变噪音 | 用户关掉开关 | 默认关闭不变；连续 3 次 + 10 分钟冷却不变；通知带原因，减少“不知道为什么” |
| CI 变慢/变贵 | 每次 >10 分钟 | 缓存 `.build`；只跑 `swift test` + archive；公开仓库 macOS 分钟免费但仍有额度 |
| 发布脚本误发 | 在脏树/错分支执行 | `--dry-run` 默认；`--publish` 需 `--yes` + 干净 main + 用户授权；失败可删 tag/Release |
| 实验数据被自己污染 | 下载数含校验下载 | 发布前记基线；只算增量；校验下载用 `curl` 不落 Release 计数（或记录并扣除） |

## 12. 版本策略

- **0.3.1（已取消）**：原计划只修安装/文案/显示名。2026-10-26 修订：H3 暂停分发、B 已全部落地且 175 项测试通过，
  从 `v0.3` cherry-pick 只增加构建与回滚面；改为直接发 0.4（决策记录见 `docs/decisions/0001-positioning.md` 文末）。
- **0.4**：B1–B6 + A/D 的产物，从当前 `main` 一次发布；`VERSION=0.4`、`BUILD=4`。
